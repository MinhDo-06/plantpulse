Lab 10 — Fault Tolerance & Resilience

ACIT 3855 · plant-water-sensor platform · before → after, decision by decision

One idea drives everything in this lab: healthchecks only protect startup — they say nothing about what happens when a dependency dies while you are running. The old design was correct on the happy path but brittle: one dead service took others down with it, and data could vanish silently. The new design has one behaviour per failure, chosen in advance.

§1The pipeline, before and after

The data path is identical in both designs. What changes is what each arrow does when the next box is missing.

Before — brittle

  • Producer uses bare send() — fire-and-forget into a buffer; nobody checks delivery
  • If Kafka is down at startup, producer.start() crashes the receiver — and nothing restarts it
  • DB-down on a GET raises OperationalError → client sees a 500 + stack trace
  • A duplicate Kafka message crash-loops the worker forever (no dedup, crash → re-read → crash)
  • Only the storage-worker has restart: on-failure

After — resilient

  • Producer is idempotent; sends are send_and_wait with a 5 s deadline
  • Kafka-down startup still refuses to start — but Docker retries until Kafka is back
  • Dependencies-down return clean 503s; /status always answers
  • Duplicates are absorbed by a unique trace_id; offsets only move after a successful write
  • Every Python service restarts on failure

Key invariant carried through every decision below: the Kafka offset is only committed after the data is safely in MySQL. That single rule is why no message is ever lost between Kafka and the database.

§2The decisions, and how each one works

Decision 1 — startup behaviour

Refuse to start, let Docker retry

Before: receiver crashes at boot when Redpanda isn't ready; container stays dead. Worker restarts, others don't.
→
After: same crash is now the mechanism: exit non-zero, restart: on-failure on all four Python services brings each back until its dependency is up.
How it works
container starts→ dependency missing → raise, exit ≠ 0→ Docker sees non-zero exit→ restarts with backoff→ dependency up → app stays up

Note the receiver's lifespan needs no retry loop — the crash is the retry. One mechanism, identical everywhere.

Decision 2 — Kafka down, receiver

Return 503 and accept the loss

Before: send() queues into a client buffer and returns 201 — the event silently dies with the buffer. Client believes it was stored.
→
After: POST returns 503 during the outage — honest failure. Once Kafka is back, sends succeed again. Events sent during the outage are accepted as lost.
How it works
POST arrives→ send_and_wait in wait_for(…, 5)→ KafkaError / TimeoutError→ logger.exception→ 503 "temporarily unavailable"

send_and_wait actually waits for broker acknowledgement (unlike send, which only fills the buffer). The 5 s deadline bounds how long a client waits before being told no. The receiver is the platform's SPOF — the lab explicitly prices this outage as acceptable data loss.

Decision 3 — MySQL down, storage-worker

Hold the offset, replay on recovery

Before: any DB error → raise → container exits. Fine for transient errors, but a re-delivered duplicate crash-loops the worker forever.
→
After: transient DB errors are retried in-process with backoff (5 attempts, capped at 30 s). Duplicates are absorbed by the unique key. The offset never advances past an unstored message.
How it works — the message journey
poll message→ save to MySQL→ success → commit offset
poll message→ DB down → no commit→ backoff, retry in-process→ DB back → same message saved → commit
poll duplicate→ IntegrityError on unique trace_id→ rollback→ commit offset, skip (already stored)

This third flow is what breaks the crash-loop: without it, "saved but offset not committed" re-delivers the same message forever. Kafka restarts mid-way are also covered: with auto.offset.reset: earliest and no auto-commit, the worker re-reads from the last commit — replay, not loss.

Decision 4 — MySQL down, storage API

GET returns 503, not 500

Before: OperationalError escapes the endpoint → framework default → 500 with a stack trace; JMeter counts it as a server bug.
→
After: DB errors are caught → clean 503, logged with context. /status still returns 200, so the container stays healthy.
How it works
GET /sensor/…→ query raises OperationalError→ except → logger.exception→ 503

Semantics: 500 means "I am broken"; 503 means "I am fine, my dependency isn't — try again". Downstream, processing's raise_for_status() turns the 503 into a skipped cycle (decision 5) instead of a crash.

Decision 5 — Storage down, processing

Skip the cycle, never reset the stats

Before: an unhandled fetch error kills the update loop → statistics freeze and the endpoint may die with them.
→
After: every cycle is wrapped: any error → log, sleep INTERVAL_SECONDS, try again. Stats file is never flushed, so recovery is automatic.
How it works
cycle starts→ fetch fails (503 / timeout)→ logger.error→ sleep 10 s→ next cycle resumes from last timestamp

Already implemented in update_loop — this decision needed no code. The polling uses ?after=<last_updated>, so after any outage the first successful fetch pulls everything missed during it: no gap, no double-count. Stats writes use a temp-file swap, so even a crash mid-write can't corrupt the file.

Decision 6 — degraded-mode map

Minimal 503; /status always alive

Before: failure semantics undefined — a service with one dead dependency behaves unpredictably across its endpoints.
→
After: each service degrades exactly the endpoints that cannot work, and nothing more.
The map

Why minimal matters: when Kafka dies, MySQL is still fine — so old events remain queryable. Degrad only what the outage actually breaks.

Decision 7 — outage detection

Detect at use-time, plus pool_pre_ping

Before: no active health polling; a pooled MySQL connection could be stale after a DB restart and fail on first use.
→
After: no separate "is it up?" loops — every operation is wrapped in try/except at the moment it runs. pool_pre_ping=True validates each pooled connection before use.
How it works
operation starts→ works → result  |  fails → except → degrade

One code path per dependency, no drift between a health-flag and reality. pool_pre_ping solves the specific case where MySQL restarted but SQLAlchemy hands you a dead connection from the pool.

Decision 8 — logging contract

Log context, never leak stack traces

Before: framework default surfaces a 500 + traceback to the client; logs may lack the context of which dependency failed.
→
After: every handler catches, logs with logger.exception (full trace in the log only), and returns a clean status code.
How it works
error occurs→ logger.exception("Kafka unavailable, rejecting reading")→ client: 503, no trace

This is the lab's observability criterion: during a chaos test, the logs alone must tell you which service is degraded and why.

§3Putting it together: one chaos timeline

The lab's test is exactly this: kill services in any order under JMeter load and watch the platform bend, not break. One pass through the worst-looking scenario:

t₀ — MySQL goes down
Worker stops committing offsets (messages pile up in Kafka, unlost). Storage API returns 503. Processing skips its cycles. Receiver keeps accepting POSTs — clients notice nothing.
t₁ — storage service stopped too
Still fine: receiver → Kafka buffered; nothing else is affected. Kafka is the shock absorber.
t₂ — MySQL back up
Worker retries succeed, replays every pending Kafka message into the DB. Storage API returns 200 again.
t₃ — Kafka goes down
Receiver degrades: POST → 503. Worker just sees an empty poll. Everything already in Kafka/MySQL is safe.
t₄ — Kafka back up
aiokafka reconnects on its own; receiver resumes; processing's next cycle pulls everything since last_updated. Statistics were never reset — the gap closes itself.
Why nothing was lost: at every instant, each message lived in at least one durable place — Kafka (persistent log) or MySQL — and the offset only ever advanced after the database confirmed the write. The only accepted loss is the receiver's 503 window in t₃, and the client was told 503, not a lie.
